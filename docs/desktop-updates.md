# 客户端自动更新

签名生产构建在每次启动、地图与个人记录可用后检查一次程序版本。设置内保留“检查更新”。程序不定时轮询。开发构建和未配置更新频道的构建不启动自动更新。

发现新版本后，后台下载并验证程序包，再准备目标版本兼容的离线资料。关闭客户端设置不会中断任务。资料准备完成后显示“立即重启更新”和“下次打开时更新”；角色、笔记、备份等弹窗打开或输入控件保持焦点时暂缓提示。下载进度和失败信息在主界面可见。

“立即重启更新”先阻止新的个人记录写入，等待已接受的操作完成，再从 IndexedDB 读取最新记录并写入本机自动备份。写入、读取或备份失败时停止安装，恢复当前界面并显示重试信息。已有写入失败时，先重试保存，再更新。Windows 使用 quiet 安装模式并要求安装器重新打开应用；macOS 安装完成后由客户端重启。

“下次打开时更新”、Escape 和点击弹窗外部均保存延期选择，本次运行不再弹出。下次启动先从缓存复验程序包，确认本地资料完整，再备份和安装。完整程序包及兼容资料均已缓存时，这一步不需要联网。手动检查可重新打开安装选择。

## 缓存与恢复

程序缓存在系统 app-local-data 的 `updates-v1/`，与个人 IndexedDB 和 `backups/` 分离。`pending.json` 保存原始更新清单、程序包 SHA256、资料代号和安装选择；`<sha256>.bin` 保存完整程序包。两个文件先在同目录写临时文件并同步，再原子替换。未完成的程序下载不登记为可安装包；重试从头下载。独立资源包继续使用原有续传机制。

每次恢复或安装均验证包哈希、Tauri 签名和签名中的目标版本。更新清单中的版本必须与签名版本一致，不能通过修改缓存版本跳过校验。正式构建继续使用原程序公钥和 GitHub Release 更新入口；测试密钥不能替换正式公钥。

程序包先落盘，再准备资料。资料准备中断后，后续启动复用程序包继续准备。资源 `state.json` 的 `update` 字段固定目标资料，防止用户先更新当前资料时清理延期更新需要的文件。若旧程序后台下载覆盖 pending，新版仍能从兼容的固定资料启动。新程序成功启动后清除安装意图并释放资料固定。

启动安装器前记录 `installing`。旧版本再次启动且仍有此标记，或安装器已返回失败时，显示上次更新未完成，不自动重复安装。用户可在设置内手动检查并重试。缓存损坏或签名失败时拒绝安装，保留当前可用版本；检查更新会重新下载可信程序包。

## 验证入口

```sh
npm test
npm run build
npm run test:e2e:updates
cargo test --manifest-path src-tauri/Cargo.toml --locked
cargo clippy --manifest-path src-tauri/Cargo.toml --locked --tests -- -D warnings
```

`test:e2e:updates` 构建桌面生产前端，使用 Edge 和测试 IPC，保留真实 IndexedDB 与界面逻辑。测试覆盖设置关闭、键盘焦点、延期重开、编辑延迟、最新记录备份、备份失败、安装中断和英文界面。该测试不调用系统安装器。

完整原生安装验收必须使用独立应用标识、独立临时密钥和测试频道。分别验证立即安装、延期后离线安装、重新启动和个人数据保留。Windows x86、Windows x64 和 macOS 的安装结果分开记录。

本轮测试结果与真实 macOS 安装证据见 [自动更新验收](desktop-updates-verification.md)。

当前正式版本 1.2.0 不会因本次源码修改获得新行为。需发布包含此实现的新客户端，后续升级才使用此流程。正式发布仍执行现有资料、字体许可和版本校验。
